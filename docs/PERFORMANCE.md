# 성능 검토 보고서 (부하 테스트·동시성)

> 이슈 #140(부하 테스트 하네스), #143(동시성 재현 테스트), Notion 「29. 서버 부하테스트」. 도구와 실행법은 [loadtest/README.md](../loadtest/README.md), 운영 측정 절차는 [docs/DEPLOY.md](DEPLOY.md) 「부하 측정」.
> 마지막 갱신: 2026-10-09 · 측정 대상 커밋: `dev` v1.11.5 + #141(시드 명령)

## 1. 요약

로컬 복제 스택(앱 2 vCPU·4GB, DB 2 vCPU·1GB, 운영과 같은 이미지·설정)에서 잰 결과다. 운영 서버는 아직 재지 않았다.

- **정상 부하는 1,000명까지 오류 없이 받는다.** 투표 상세를 열어 둔 사람 300명은 114 req/s에 상세 p95 39ms, 앱 CPU 최대 89%(2 vCPU = 200% 기준), 1,000명은 283 req/s에 p95 40ms·p99 86ms, 실패 0이다. 다만 1,000명에서 앱 CPU가 한도(213%)에 닿고 DB도 165%라 **상한은 메모리가 아니라 CPU**다(힙은 1,000명에서도 359MB). 2 vCPU 서버라면 동시 시청자 약 1,000명이 여유 없는 상한이고, 300명은 절반쯤 쓴다.
- **문제는 「동시에 몰리는 순간」이다.** 탭 포커스 버스트(한 사람이 9개 요청 동시)를 100명이 같이 일으키면 상세 p95가 3.4초, 300명이면 4.5초, 1,000명이면 9.3초가 된다(Hikari 대기 최대 187). 앱 재시작 직후 300개 소켓이 1초 안에 재연결하면 핸드셰이크 p95 3.4초지만 10초로 분산하면 12ms다. 점심 피크(전원 동시 진입 + 마감 직전 참여 폭주)에서는 300명 기준 참여 p95 1.24초, 1,000명 기준 상세 p95 2.3초·참여 p95 3.7초이고 **Tomcat 연결 대기열이 넘쳐 502(connection reset) 355건**이 났다.
- **원인은 요청마다 드는 고정 비용과 10개뿐인 커넥션 풀이다.** 요청마다 세션 SELECT+UPDATE 2문장(총 시간 2·3위), 상세 폴링마다 멤버 전원의 프로필 전체 컬럼을 읽는 쿼리(총 시간 1위, 20분에 400만 행)가 전체 DB 시간의 절반을 넘는다. 느린 쿼리(200ms 초과)는 하나도 없었다. 지난 투표 500일치가 있어도 자동완성 CTE는 9.4ms라 풀 고갈로 이어지지 않았다.
- **동시성 결함 4건을 결정적으로 재현했다**(#145~#148): 「지금 마감」 뒤 참여 반영·마감 되돌림(k6에서도 6회 중 3회 관찰), 느린 소켓이 요청 스레드와 DB 커넥션을 묶음, 초대 참여의 멱등성과 마지막 멤버 탈퇴 때 멤버십 소실, 동시 메뉴 추가 문구. 계획 때 걱정한 강제 탈퇴 교착은 없었다(Hibernate 7이 `FOR NO KEY UPDATE`를 쓴다).
- 권장 조치의 우선순위는 7절이다. 수정은 모두 별도 이슈이고, 다음 측정은 #145·#146을 고친 뒤 운영 심야(300명까지)다.

## 3. 수용량 (steady · focus-burst)

**정상 부하(`steady`)**: 「투표 상세 화면을 열어 둔 사람」 N명. 단계마다 5분 유지, 세션 10분마다 재진입.

| 동시 사용자 | 요청/초 | 상세 GET p50 / p95 / p99 | 참여 PUT p95 | WS 연결 p95 | 실패 | Hikari active / pending 최대 | 앱 CPU 최대 | DB CPU 최대 | 힙 최대 | GC pause 누적 |
|---:|---:|---|---:|---:|---:|---|---:|---:|---:|---:|
| 300 | 114 | 14.8 / 38.6 / 65.9 ms | 33.6 ms | 20.8 ms | 0 | 7 / 0 | 89% | 66% | 266 MB | 1.35 s (13분) |
| 1,000 | 283 | 13.7 / 40.3 / 86.0 ms | 41.6 ms | 25.9 ms | 0 | 10 / 32 | 213% | 165% | 359 MB | 4.30 s (20분) |

CPU는 컨테이너 한도 2 vCPU = 200% 기준이다. 1,000명에서 앱이 한도에 닿았고(k6도 같은 PC에서 돌아 실제 여유는 이보다 조금 더 있다) 커넥션 풀이 순간적으로 가득 찼다(pending 32). 상세 폴링이 전체 요청의 55%(156 req/s)다.

**버스트(`focus-burst`)**: 창으로 돌아올 때 나가는 9개 요청(me·조직·오늘 투표·상세·채팅 목록·쪽지·방명록·제재·version.json)을 N명이 같은 순간에.

| 동시 사용자 | 요청/초 | 상세 GET p50 / p95 / p99 | 오늘 투표 p95 | Hikari pending 최대 | 앱 CPU 최대 |
|---:|---:|---|---:|---:|---:|
| 100 | 74 | 0.6 / 3.4 / 3.9 s | 3.5 s | (10초 샘플에 안 잡힘) | 33% |
| 300 | 194 | 1.1 / 4.5 / 5.6 s | 4.8 s | (10초 샘플에 안 잡힘) | 52% |
| 1,000 | 396 | 4.4 / 9.3 / 10.4 s | 9.4 s | 187 | 220% |

실패는 0이지만 응답이 수 초다. 900~9,000개 요청이 한꺼번에 커넥션 10개에 줄을 서는 모양이고(100명 기준 CPU는 33%뿐), 그래서 느린 쿼리 없이도 기다린다.

**수용량 판단**: 평상시(점진적 진입)는 2 vCPU로 1,000명까지 받는다. 그러나 점심 11:55~12:00처럼 수백 명이 1분 안에 동시에 진입하거나 탭을 다시 열면 수 초씩 기다리고, 1,000명이 동시에 진입하면 502가 난다(4절 점심 피크). 목표 300명은 정상 부하에서 합격(p95 39ms < 500ms, 오류 0), 피크에서는 참여 p95 1.24초로 목표(800ms)를 넘겨 **조건부 합격**이다.

## 6. 병목과 근거

근거는 `loadtest/out/<실행>/`의 k6 요약, actuator 스냅샷(`report.py`), `pg_stat_statements` 상위 쿼리, Caddy·앱 로그다.

1. **커넥션 풀 10개에 버스트가 줄을 선다.** 포커스 버스트·동시 진입·재연결 폭풍에서 `hikaricp_connections_pending`이 17~191까지 올라가고 응답이 수 초가 된다. 느린 쿼리는 없고(200ms 넘는 문장 0건) 요청당 짧은 문장이 7~10개라, 묶음이 한꺼번에 오면 풀이 병목이 된다. Tomcat 스레드 200개가 커넥션 10개를 기다리는 구조다.
2. **요청마다 드는 고정 비용이 크다.** `pg_stat_statements` 총 시간 상위는 어느 실행에서나 같다: ① 상세 폴링의 멤버 목록 쿼리(`MembershipRepository.findMembers`, 20명 × 프로필 전 컬럼: 1,000명 20분에 199k회·398만 행·65.6초), ② 세션 UPDATE(`SPRING_SESSION … LAST_ACCESS_TIME`, 350k회·37.6초), ③ 세션 SELECT(351k회·30.7초). ②+③이 ①과 맞먹고, 셋이 DB 시간의 절반을 넘는다. 로그인한 요청은 정적 파일이 아니면 전부 세션을 읽고 쓴다.
3. **상세 3초 폴링이 전체 요청의 55%다**(1,000명에서 156 req/s). 응답은 메뉴별 참여자·패스·미응답자 명단 전체라 멤버 수에 비례해 커진다. 채팅은 이미 WebSocket이 있는데 투표 변경은 폴링으로 받는다.
4. **동시 진입 때 Tomcat이 연결을 거부한다.** 1,000명 점심 피크에서 502 355건, 300명에서도 5건. Caddy의 `connection reset by peer`이고 앱 로그에는 아무것도 없다. `server.tomcat.accept-count` 기본 100(대기열)이 넘치면 커널이 연결을 리셋한다.
5. **WebSocket 재연결에 지터가 없다.** 같은 1초에 몰리면 핸드셰이크 p95 3.4초(300)·7.7초(1,000), 10초에 분산하면 12ms. 핸드셰이크마다 멤버 확인 2쿼리 + 세션 읽기·쓰기가 들고, 연결마다 채팅 목록 GET이 따라온다.
6. **앱 CPU가 1,000명의 상한이다.** 정상 부하 1,000명에서 앱 213%·DB 165%(각 2 vCPU 한도). 힙은 359MB로 2GB 한도에 여유가 많고 GC 중단은 20분에 4.3초다. 메모리를 늘려도 수용량은 늘지 않는다.
7. **마감 순간의 경합**(5절 #145): 참여 폭주 중 「지금 마감」이 들어오면 결과 명단이 마감 뒤 한 번 바뀐다. 6회 중 3회.
8. **느린 소켓 하나가 커넥션 하나를 묶는다**(5절 #146): 채팅이 활발한 투표에서 느린 모바일 연결이 몇 개면 풀 10개가 그만큼 준다. 부하 테스트에서는 k6 소켓이 빨라 드러나지 않았고 통합 테스트로만 확인했다.
